# ADR-010: emulator_6502 as the 6502 core of score64-emu, behind a CPU trait

**Status:** Accepted
**Date:** 2026-10-18
**Deciders:** @jahaa

## Context

`score64-emu` (GPL-3.0-or-later, ADR-002) runs the real packed GoatTracker player: init once, play at 50 Hz, with every SID write passed to the SID emulation at the cycle it happens (TAD §5.1). It needs an NMOS 6502 core that:

- has a licence compatible with GPL-3.0-or-later,
- gets documented opcodes, flags and decimal mode right,
- reports how many cycles each instruction takes, so SID writes can be timestamped inside the 19,656-cycle PAL frame,
- handles the stable undocumented opcodes, because players other than GoatTracker's, and our own audition driver, may use them,
- is maintained, or small enough that we could own it.

Bus-exact behaviour (dummy reads and writes on the right cycle) only matters if a player reads or read-modify-writes registers with side effects. The GoatTracker player writes the SID and does not read it back, so per-instruction accuracy is enough to start.

## Method

Each candidate ran the [SingleStepTests/65x02](https://github.com/SingleStepTests/65x02) NMOS vectors (`6502/v1`, MIT): 10,000 random cases for each of the 256 opcodes, 2.56 million in all. Each case sets up the registers and RAM, runs one instruction, and checks the final state, the cycle count and the per-cycle bus log. The harness and the raw results are in [`crates/score64-emu/spikes/cpu-conformance/`](../../crates/score64-emu/spikes/cpu-conformance/README.md).

The 12 JAM opcodes are left out. The 7 unstable opcodes (ANE, LXA, SHA ×2, SHX, SHY, TAS) are reported but not weighted, because real chips disagree on them. One JSR case fails on every core: the stack overlaps the JSR operand. That case can't occur in a player.

## Results

| Crate (version, licence) | Documented (151): state / cycles | Decimal ADC/SBC | Stable illegal (86): state / cycles | Bus-exact | Last release |
|---|---|---|---|---|---|
| **`emulator_6502` 1.1.0, MIT** | **100.00 % / 99.67 %** | **100 %** | **99.44 % / 100 %** | 36 % | 2021-02 |
| `mos6502` 0.10.1, BSD-3-Clause | 97.38 % / 98.02 % | 75 % | 95.45 % / 89.59 % | 39 % | 2026-06 |
| `mos6502_model` 0.2.1, MIT | 95.52 % / 99.34 % | 58 % (no decimal mode) | 91.22 % / 98.84 % | 36 % | 2023-02 |
| `zinc64-emu` 0.8.0, GPL-3.0+ | 97.10 % / 89.74 % | 75 % | 4.63 % (panics) | 39 % | 2019-05 |

Where each one falls short:

- **`emulator_6502`**: `STA (zp),Y` ($91) takes 7 cycles instead of 6 when the address crosses a page. ARR ($6B) is wrong in decimal mode. JAM opcodes panic. There are no dummy bus cycles: an instruction does all its reads and writes on its first cycle and then idles for the rest.
- **`mos6502`**: read-modify-write `abs,X` instructions (ASL, ROL, LSR, ROR, INC and DEC, $1E–$FE) and their illegal RMW counterparts add a page-cross cycle they shouldn't have. Decimal-mode results or flags differ in about 25 % of the random ADC/SBC cases. It is actively maintained and takes pull requests.
- **`mos6502_model`**: written for the NES (Ricoh 2A03), so ADC and SBC ignore decimal mode, and `(zp),Y` reads in ORA and AND are off by one cycle on page crossings.
- **`zinc64-emu`**: most undocumented opcodes are missing and panic. Reads of $00/$01 go to the 6510 port, which is correct on a C64 but fails the plain-6502 vectors. The crates.io release is from 2019. Upstream (`binaryfields/zinc64`) was rewritten in 2025 and that version isn't published.

Not run: `r6502` and `yamos6502` don't count cycles, and `w65c02s` emulates the 65C02 (CMOS), not the NMOS 6502.

## Decision

Use **`emulator_6502` 1.1.0** (pinned exactly, features `illegal_opcodes` and `binary_coded_decimal`) as the 6502 core, and only in `crates/score64-emu`. Put it behind a small `Cpu` trait in that crate (step one instruction, return the cycles taken and the bus accesses), so the core can be swapped without touching the protocol or the SID side. The wrapper:

1. checks the opcode before each step and returns a "CPU jammed" error for JAM opcodes, instead of letting the crate panic,
2. corrects the `STA (zp),Y` page-cross cycle,
3. timestamps each write on the instruction's last cycle (an RMW's dummy write goes on the cycle before), matching where the 6502 really puts it,
4. runs a conformance test against a committed subset of the SingleStepTests vectors (documented and stable undocumented opcodes) in `score64-emu`'s tests.

## Options considered

### Option A: `emulator_6502` (chosen)
| Dimension | Assessment |
|---|---|
| Complexity | Small API: an `Interface6502` read/write trait and `cycle()` / `execute_instruction()` |
| Performance | One frame of a GoatTracker player is a few thousand cycles; any of these cores runs far faster than real time |
| Maintenance | No release since 2021; MIT, so a fork can live inside `score64-emu` if we need more than the two wrapper fixes |
| Fit | The most accurate per instruction, including decimal mode and the stable undocumented opcodes |

### Option B: `mos6502`
| Dimension | Assessment |
|---|---|
| Complexity | Similar API (`Bus` trait, `single_step`, a `cycles` counter) |
| Maintenance | The only actively maintained candidate |
| Fit | The RMW `abs,X` cycle errors land on instructions players use, and decimal mode is off. Both are fixable upstream, but that's work in someone else's repository before we can rely on it |

### Option C: `zinc64-emu`
| Dimension | Assessment |
|---|---|
| Fit | Missing undocumented opcodes, an unmaintained release, and the CPU is tied to zinc64's shared-pin and IRQ types |

### Option D: write our own bus-exact NMOS core in `score64-emu`
| Dimension | Assessment |
|---|---|
| Complexity | About 1,000–1,500 lines; the harness above already gives full per-cycle test coverage |
| Fit | The only way to be bus-exact. Not needed yet, because the GoatTracker player doesn't read the SID |

## Trade-off analysis

`emulator_6502` is the only candidate that passes every documented opcode, decimal mode included, and nearly every stable undocumented one. Its two cycle-level problems can be handled in our wrapper and are covered by tests. Its weakness is maintenance, not correctness, and the MIT licence lets us fork it into the GPL helper if that changes. `mos6502` would be the choice if upstream fixed its RMW cycles and decimal mode, and the `Cpu` trait keeps that switch cheap. Option D stays the fallback if bus-exact behaviour turns out to matter.

## Consequences
- Easier: #20 can start right away on a well-tested core; the conformance harness is reusable for any later core.
- Harder: we own two workarounds and the JAM handling in the wrapper, and a crate that gets no upstream fixes.
- Revisit when: the oracle comparison with sidplayfp (#20, #59) shows timing differences that trace back to the CPU; a player we support needs bus-exact reads (for example polling `$D41B` / `$D41C`); or `mos6502` fixes the issues above.
